# EVCS 演算法驗證測試 — 方案說明 (High-Level Spec) v1

**目的**：為 EVCS 功率分配演算法建立系統性驗證。在開發者無法預先規劃完整事件序列的限制下，以探索方式長時間驅動系統走遍大量合法狀態，並驗證演算法的自洽、合法、守恆。
**核可請求**：確認方法可行性後，進入實作。

> 本方案經三輪程式碼調查（狀態空間、穩態頻率、既有設施複用）實證，確認可行性與實作路徑。

---

## 1. 問題：原狀測試無法保證覆蓋完整

現行測試是針對特定場景手寫的原狀。隨著 FR-10（多 MCU）/ FR-11（模組功率）解鎖，**(8 樁佔用配置, 來車 SOC)** 的組合爆量級增長，手寫原狀無法證明「沒有漏掉組合」。需要一個能系統性嘗試大量狀態的方法，補足手寫原狀與線上實戰流量都照不到的角落。

## 2. 狀態空間建模

- **節點 = `(O, L)`**：O = 8-bit 佔用向量（每樁是否有車，2⁸=256 種），L = 最後來車 SOC（低/中/高），空站為無值。合計 **766 個合法節點**
- **邊 = 一次事件**：車輛進場（arrive）或離場（depart），各使恰好一個樁進或出

| 維度 | 取值 |
|---|---|
| 充電樁數量 | 8（固定） |
| 來車 SOC | 低 / 中 / 高 |
| 站內初車 SOC | 低 / 中 / 高（L 維度） |
| 車種 | 1（固定） |

> 為何分母是 766 而非對稱化簡後的 ~208：在「每 MCU 功率相同」的假設下，才能對稱地把 256 種佔用壓縮成約 70 類。但本系統開啟 FR-11（每 MCU 功率可不同），對稱被打破，故採 766 為主分母（誠實反映真實配置）；另回報「車類覆蓋」作診斷視角。

## 3. 核心限制（開發者無法預先設計完整劇本）：已實證

本方案的根本前提，且已經程式碼調查確認：

| 測試端可控 | 測試端不可控 |
|---|---|
| ✅ 下一台車進場時機 | ❌ 離場時機 |
| ✅ 下一台車 SOC | ❌ 離場目標車 |

**實證**：車輛充到目標 SOC 時，系統會自動觸發離場，由內部充電進度與功率分配決定誰先走。**測試完全不參與、也無法主動指定離場。**

**後果**：無法寫死完整事件序列——即使最好計畫，幾個邊到達時系統可能已因自發離場走到別的狀態。**故放棄預先規劃路徑，改為探索式即時抽樣。**

## 4. 方法：探索式即時抽樣

測試只控制進場、被動觀察離場，邊走邊記錄、邊驗證。

- **進場挑選（覆蓋導向）**：每次發車前，貪心選擇「能走到未訪節點」的時機與 SOC；站滿則按兵。直推進更等系統自然離場
- **時間模型**：模擬時間可快轉（直計算），預算上限模擬 24 小時
- **終止（回到原點）**：模擬時間達上限 ∥ 節點覆蓋到門檻 ∥ 連續多步無新節點
- **可重現**：固定亂數種子，失敗可重現

### 覆蓋率是觀察數據，不是通過判據

本方案**不保證 100% 覆蓋**。有些狀態因演算法分配策略而難以達到。**覆蓋率本身即是對演算法行為分布的觀察輸出**——覆蓋率低是下一輪迭代要改善的事，非本步驟失敗。

## 5. 雙軍驗證

程式碼調查實測：系統自由運行時頗久時間處於穩態，故大部分驗證可在穩態做。但部分驗證屬於「每一個時間步都必須成立」的性質：穩態或切換中經過的瞬時都重要。故分性質分兩支軍：

| 軍 | 驗證項目 | 時機 |
|---|---|---|
| **穩態軍** | 守恆正確、功率借還借貸守恆、MCU 鄰居一致 | 系統自然到穩態時 |
| **逐-tick 軍** | 系統不變量（如充電中 relay 須恆為閉合）、relay 切換順序 | 每一個時間步 |

**驗證基準**：本測試**不重寫一套功率分配演算法作為對照**，因其工作量等同重做核心、且會複製既有 bug。改以「一致性 + 守恆 + 合法性」為基準。絕對最佳值由已交付且 user 無錯誤回饋的線上系統隱性背書。已知缺口：若在高 MCU 一致地產出合法但非最佳的值，本法不另設對照偵測——該風險由線上實戰覆蓋。

## 6. 風險可控：複用既有設施、不碰 production

- 程式碼調查確認：engine **已內建大量可複用的驗證設施**（逐 tick 檢查餘存、鄰居一致性比對、每 tick 狀態快照）。測試僅新建小薄層（進場挑選、覆蓋追蹤、穩態判斷、少數既有設施未涵蓋的檢查），其餘**直接複用**
- 進場以系統既有底層接口注入；離場不主動觸發，僅被動觀察
- 車跡記錄複用 engine 既有的每-tick 快照
- **不修改任何 production code**：完成後的版本控制應顯示新增測試檔案

## 7. 交付與驗收

- **交付物**：探索式主測試、進場挑選器、覆蓋追蹤器，以及複用既有設施的薄封裝層
- **通過判據**：**所有走過的穩態 + 每個時間步的逐邊驗證**；離場全由系統自發，production 未修改
- **不作為判據**：覆蓋的數值——觀察輸出，但覆蓋低代表須再迭代，但本步驟視為完成
- **價值**：建立可重複的探索式回歸框架，未來演算法改動可比對「走過狀態 + 驗證結果」差異；覆蓋率變動亦反映演算法行為改變

## 附錄：方法演進說明

本方案早期曾規劃以「預先生成的分配歷路徑（DFS）」做系統性覆蓋所有可達態轉移。但經程式碼調查確認**離場由系統內部自發觸發、測試無法預先規劃**，該前提不成立，故改為現行的**探索式即時抽樣**。驗證內容（分層檢查）完整保留；改變的是「驅動系統走遍狀態的方法」——從預先規劃改為即時探索。
